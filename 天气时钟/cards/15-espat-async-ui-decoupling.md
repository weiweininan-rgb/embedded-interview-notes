# ESP-AT 异步与 UI 解耦

## L1 电梯陈述

教程 v6 把“联网/业务逻辑”和“真正写 LCD”拆开：业务侧把显示请求送入 UI 队列，UI 任务独占显示资源并依次绘制。这能避免多个任务直接争抢 LCD/SPI，也让网络处理不必同步等待每次刷新完成。

## L2 架构与数据流

```text
Wi-Fi / 时间 / 天气业务
  → 生成显示动作和必要数据
  → UI 接口投递 ui_message_t
  → UI 任务从 ui_queue 接收
  → UI 任务操作 ST7789 并完成绘制
```

UART 接收、AT 事件、+IPD 长度负载收满、HTTP/JSON 业务解析仍应分层：串口接收只是连续字节流，不能把“一次接收”或“一个换行”直接当作一条完整天气报文。教程的 UI 解耦不等于所有网络异常都已经具备完善恢复策略。

## L3 机制深挖

UI 队列与单写者架构优先解决“谁能写 LCD”的问题，因此教程 v6 没有在应用/驱动代码中创建 Mutex。若架构改成多个任务直接写 SPI/LCD，则应让一个任务独占，或用 Mutex 围住完整事务；二值信号量不能替代资源所有权保护，也没有 Mutex 的优先级继承语义。

### 已确认源码边界：Wi-Fi 失败路径可能压住 UI

- 教程 v6 的 `main.c::main_init()` 以优先级 9 创建为 `init` 任务。正常路径中，`wifi_wait_connect()` 返回后才会继续 `main_loop_init()` 并执行 `vTaskDelete(NULL)`。
- `wifi.c::wifi_wait_connect()` 的连接失败路径先调用 `error_page_display("wireless connect failed")` 提交 UI 请求，随后进入 `while (1) { ; }`。该路径不会返回 `main_init()`，因此不会走到末尾的 `vTaskDelete(NULL)`。
- 结果是 `init` 任务会以优先级 9 持续就绪，而 UI 任务优先级为 8；按抢占式优先级调度，UI 请求可能已入队但 UI 任务得不到 CPU 绘制错误页。这是基于源码控制流和优先级的推理。
- 改进方向是在提交错误 UI 请求后让 `init` 阻塞、挂起或删除自己，以让 UI 任务获得运行机会；具体故障恢复策略应结合产品需求决定。

#### 推荐故障处理方案

若当前产品策略是“显示错误页后停止本轮启动”，可在 `wifi_wait_connect()` 的失败路径中提交 UI 请求后删除当前 `init` 任务：

```c
error_page_display("wireless connect failed");
/* UI 请求已入队；此时仍不能进入高优先级空转。 */

vTaskDelete(NULL);
/* 删除当前 init 任务，让优先级 8 的 UI 任务获得 CPU 并绘制错误页。 */
```

这只是改进建议，不是教程源码已实现的行为。若产品需要自动重连，应改为由普通任务按退避周期重试，或由明确的恢复状态机等待事件；同样不能让高优先级任务以 `while (1) { ; }` 空转。

## L4 权衡与替代方案

将 UI 收敛到一个任务，代价是消息结构、队列容量和字符串所有权必须设计清楚；收益是 LCD/SPI 的并发边界明确。启动失败时，最小修正是错误 UI 请求入队后让 init 删除或阻塞；若需要自动恢复，可改为普通优先级的重连任务加退避周期和明确状态机。以上均为基于源码的改进建议。
